- Live Preview 仅在源文本改变时刷新文档结构；纯选区及 IME composing 更新
  继续同步活动块和源码位置。
- 内部计数器覆盖 `_refreshBlocks`，包括引用、跨段高亮、脚注、块和标题折叠。
  它不代表所有渲染器或 Controller 内部的解析次数。
- 新增跨段选区、双向 composing 映射以及编辑、撤销、重做回归；已有布局、
  表格、折叠、导航和源码映射测试继续运行。
- `IANVS_MARKDOWN_FORCE_DOCUMENT_PARSE` 只用于复现优化前的刷新行为。
  前后对比使用相同源码、语料、测量脚本和 SDK，只改变此诊断开关。

## profile 运行发现的问题

### 表格读取 debug 专用状态

最低 SDK Flutter 3.44.0 的 profile 运行在表格布局完成回调抛出：

```text
LateInitializationError: Local 'result' has not been initialized.
RenderObject.debugNeedsLayout
_EditableMarkdownTableState._syncTableHandleLengths
_EditableMarkdownTableState.build.<anonymous closure>
SchedulerBinding._invokeFrameCallback
```

SDK 中该 getter 的局部变量仅在 assert 内赋值，profile/release 禁用 assert
后读取会抛异常。组件已改为检查 `hasSize`，只在 `kDebugMode` 时额外读取
`debugNeedsLayout`。普通 widget 测试启用 assert，无法单独验证此问题；
含表格语料的 profile 运行是必要补充。

### macOS AOT 构建限制

本机未修改的 Flutter 3.44.0、3.44.8 和 3.47.6 在 profile 编译阶段均遇到
`_window_macos.dart` / `_Rect` 的 illegal cid 错误，见
[Flutter #191575](https://github.com/flutter/flutter/issues/191575)。
测量使用临时 SDK 禁用实验性 windowing 分支的单行补丁；完整补丁和哈希
随结果保留。该方法用于隔离组件性能，不能作为未修改 SDK 的发布构建验收。
用户日常使用的 Flutter SDK 没有修改。

### 无效采样的处理

早期一次探索运行未验证 `package:flutter` 实际路径，结果已弃用。
后续 Flutter 3.47.6 尝试在 1 MiB 完整渲染的模式切换阶段十多分钟未完成，
进程仍消耗 CPU，人工终止；没有生成可接受的完整基线，也没有据此归因到
某个解析或布局算法。最低 SDK 的表格异常采样同样弃用。

脚本现已显式解析并校验 framework 路径，逐阶段保存数据，遇首个渲染异常
即停止；每阶段默认 180 秒超时。后续诊断可直接读取最后完成阶段及错误，
不必等待整组结束。测量方法、指标口径和命令见 [README](README.md)。

## 后续验收规则

2. 两组均须 `complete: true`、`errors: []`，并覆盖六个场景、五类操作。

5. 多次独立进程复测以确定方差，再制定延迟和内存门槛。当前仅将可重复

### 完整度与限制

- 优化前：29/30 个阶段完成；`complete: false`。Timed out: 1048576 bytes / unlimited-controlled-corpus / modeSwitch after 180 seconds
- 优化后：29/30 个阶段完成；`complete: false`。Timed out: 1048576 bytes / unlimited-controlled-corpus / modeSwitch after 180 seconds

超时指包含预热在内的整组阶段未在 180 秒内完成，不能推导为某一次切换耗时超过 180 秒。
下列分项在超时发生前完成，没有渲染异常，仅作为局部诊断证据。未完成阶段没有 P95，也没有以默认预算回退成绩替代。

### 帧耗时和内存

取每个场景中**已完成操作各自的 P95 的最大值**，不是将全部帧合并后求 P95。RSS 是完成动作后的进程采样最大值，包含引擎、缓存、原生库和历史，不是 Dart 堆或精确峰值。未完成模式切换的内存未纳入。
各场景顺序运行，垃圾回收时机也会影响 RSS；不能据此单组采样认定内存改善。

### 下一轮具体步骤

1. 为脚本增加场景筛选，将 Source、Reading、Live 的转换独立测量，逐样本落盘；先定位超时，不把整组阶段超时写成单次操作延迟。
2. 对 1 MiB 无预算路径采集 CPU/布局证据，区分源码样式生成、完整 Reading 布局及 Live 重建；确认需要优化的路径后再改实现。
3. 将全文结构刷新拆分计时，优先降低文本输入和首次展示的成本；保持引用、脚注、折叠、表格及撤销语义。
4. 修复或明确支持边界后重新取得完整配对结果，并做多次独立进程复测，再建立延迟/RSS 门槛。R0-04 在此之前保持「进行中」。
