## 归因结果（不计验收）

两个实际 Profile main 以 `d2fea8b` 加临时保存分段构建，10 KiB、5 次预热 / 20 样本。
TK2 控制仅移除两宿主 override；源码冻结可直接比较。原 SDK、全文、字体和预算不变。
有效对照如下，单位 ms，P95 为第 19 / 20 项。

| 入口 / 操作 | TK1 P95 | TK2 P95 | 判断 |
| --- | ---: | ---: | --- |
| example Source→Read | 95.849 | 92.991 | 未重现上一批 206.507 ms；不删除旧失败 |
| app Live type | 40.283 | 41.703 | 小文档额外成本未随 TK2 消失 |
| app Live paste | 41.542 | 42.798 | 同上 |
| app save | 30.602 | 28.981 | 单轮波动不能证明 TK2 优于 TK1 |

保留之前已获人工复核且改善 1 MiB 的受限 TextKit 1 实现。此次没有修改 SDK、原生输入、
菜单、composing 路由或语义开关；TK2 控制及临时保存分段已撤回。

CPU 证据支持三项局部处理：

- example Source→Read 的 1,161 个 CPU 样本中，代码纹理函数包含 155 个，`Path.addRect`
  顶层 128 个。每次重建都逐点创建相同背景路径；改为有界几何路径复用，仍按原方式矢量绘制。
- app save 的 285 个 CPU 样本中，源码着色包含 168 个。第 5 个样本文件写入 2.069 ms，
  会话持久化阶段墙钟 24.226 ms，而着色 CPU 出现在动作开始后 6.913–15.815 ms，处于此阶段内。
  因此该阶段并非纯磁盘时间：保存通知触发同步着色，会延后异步 I/O 完成回调。
  优化复用当前编辑值及完整样式相同的 TextSpan，不改变保存顺序、flush 或恢复持久化。
- app Live type/paste 中，controller 与 Live 分别解析同一份引用定义；type 两者各约 16 个正则
  CPU 样本。Live 可复用 controller 在监听器前更新的不可变引用表；若 controller 预算更严，
  则继续按 Live 自身预算解析，不放宽任一处理边界。

早期逐动作 `getCpuSamples` 查询制造额外长尾：example 第 8 / 16 项约 272 / 274 ms，
CPU 多次停在 VM safepoint；改为整轮完成后查询，95.849 ms 对照不再出现该异常。
这只解释诊断工具扰动，**不能解释上一批没有 CPU 查询的 206.507 ms**。
工具补充完成前禁止 CPU 查询、无效轮拒绝提取、递归栈正确计数及零 CPU 区间保留回归。

两次失焦尝试保留并排除；结果、trace、构建冻结、CPU 区间及临时补丁见
[证据目录](results/2026-10-15-small-document-latency/README.md)。

## 候选实现与验证计划

源码着色仅保留当前一份值，文本、选区、composing、withComposing、正文样式及全部语法样式
任一改变都失效。Live 复用引用表不改变全文、历史或命令行为。背景缓存最多 8 条路径，
每条最多 32,768 格，超限仍完整绘制但不保留；不持有源码或位图。

批量点绘制实验在 1.25 倍缩放产生像素差异，已放弃；改用原 Path 绘制。
新增三项回归覆盖保存/重建复用与失效、引用编辑/撤销及预算、18 组背景逐像素对照。
针对性回归通过。完整回归及两入口各两轮正式配对尚在进行，R4-03 暂不关闭。
