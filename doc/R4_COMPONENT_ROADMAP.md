## 目标和范围

让 `ianvs_markdown` 在长文、反复切换和持续编辑中更易复用。组件库负责完整 Markdown、
源码范围、命令、输入/选区、视口行为和资源生命周期；example 演示最小可理解的接入，
app 验证真实文件和多文档使用。文件读写、授权、工作区和系统菜单的外壳仍归宿主。

固定入口为 `example/lib/main.dart` 与 `app/lib/main.dart`。需要切换语料、诊断或模拟慢回调时，
在这两个入口内提供受控选项；不新增可执行 main、独立验收 app 或仓库外产品接入前置。
保持原版已验证 SDK；旧独立 benchmark 只作归因参考，不能直接充当新主入口成绩。
默认资源不自动联网或读文件，预算不截断保存原文，版本保持 `0.3.1` + `Unreleased`。

稳定崩溃时，立即提升为 P0 并先修复。P1 解决当前高频操作及其必要测量；P2 增加日常能力和
长期验证。规模表示耦合程度，不是工期承诺：中等通常跨组件与宿主；大项可能涉及布局/输入架构。

## R4-01 命令路由和输入边界一致

**使用场景：** example 编辑 YAML 属性时点原生 Undo；app 在表格、正文和侧栏之间
切换后使用菜单；中文正在 composing 时调用菜单或模式切换；宿主重映射/保留快捷键。

交付：先形成键盘、原生菜单和工具栏的命令矩阵，明确作用域、局部/文档历史、组合输入以及
可用状态。复用核心已有命令路由，只有两个入口都需要时才增加通用调用接口；菜单结构、
文件命令和窗口操作留给宿主。键位禁用与“禁用操作”是不同概念，不能未经决策就等同。

验收：

- 原生 `Menu.selectedCallback` 与实际快捷键分别测试；覆盖正文、表格、Read 和非编辑控件。属性局部历史在 example 验证；app 当前 `showFrontMatter: false`，不为验收另开属性界面。
- 编辑属性时撤销作用于预期局部历史；非编辑控件不会误改正文；组合输入不被命令静默丢弃。
- 自定义快捷键不被原生默认 accelerator 抢走；菜单显示/可用性遵循明确的宿主策略。
- 两个 Release main 人工复核菜单操作；若改变 composing 路径，重做两模式中文确认/取消。
- 若风险未复现，也必须记录路径、预期与回归覆盖；不为消除代码重复而扩大公共 API。

建议提交：行为矩阵与失败回归 → 核心最小路由/宿主接线 → 主入口验证与 API/迁移记录。

## R4-02 两个 main 的交互性能基线

**使用场景：** 用户在实际窗口载入 10 KiB、100 KiB、1 MiB 文本，输入、粘贴、切模式和回到文档尾部。
旧 `tool/run_benchmark.py` 指向独立 `benchmark/live_editor_benchmark.dart`，本任务不能直接重跑它来关闭验收。

交付：在现有 main 中加载可重放的合成语料/临时文件，并提供默认关闭的诊断采样；入口、
页面树和宿主保存流程不替换成 benchmark 专用应用。已有输入/trace 校验器可复用。
记录默认预算下的 Source/Live 输入、粘贴、模式切换；app 另记打开/保存时间，分离磁盘与编辑耗时。

验收：

- 冻结 SDK、源码、窗口、字体、语料哈希、预算、构建模式和动作定义；记录实际降级分支。
- 每个入口至少两次串行完整基线；每个选定动作至少 5 次预热 / 20 次样本。正式前写清场景矩阵，不能测后删慢项。
- 分别报告动作回调、到下一帧、帧时长、RSS 及原始样本；合成输入、物理输入和 CUA 往返严格分开。
- 前台丢失、窗口改变、缺样本或异常需标无效并归档；采样期间不并行构建。
- 使用原版 SDK、同一构建模式做后续配对。Profile 若在实际 main 无法运行，记录失败并评估同模式 Release 测量，不能通过 SDK 补丁或新宿主绕过。
- 产出可复验观察线和问题排序，默认诊断关闭；本任务只建立事实，不把测量本身记为性能改善。

建议提交：两个入口语料/采样接线 → 数据格式及有效性校验 → 两轮结果与 R4-03 目标。

R4-02 实际交付：同一 `3956a01` / 原版 Flutter 3.44.8 / Profile，example 和 app 各两轮
完整有效，2,400 正式 + 600 预热；六次无效轮次保留。协议、60 个场景的观察线、合成输入
边界、帧归属和文件子区间见 [性能报告](../benchmark/MAIN-ENTRY-PERFORMANCE-2026-10-13.md)。
10 KiB 为完整 Markdown；100 KiB/1 MiB 为默认 syntaxTokens 降级，未截断编辑/保存原文。
本项不记为性能改善，旧独立入口没有补入本轮数据。

## R4-03 大文档编辑成本优化

**使用场景：** 文档超预算后能继续编辑，但完整 TextField 排版、源码扫描和历史仍可能拖慢输入。

交付：根据 R4-02 区分 Controller/解析、Flutter 排版、历史与宿主存储成本。先选影响最大的
一条路径做小改动；大范围 Source 分块/虚拟化只在较小改动不能达到目标时进入方案评审。
不能通过更早截断原文、关闭选择/IME、缩小测试语料或偷偷放宽预算换取成绩。

R4-02 后的起点：优先归因 example 默认预算 1 MiB Read→Live（两轮 P95 2625.868 /
2672.944 ms，回调小于 0.1 ms，归属帧约 66 ms，必须解释其余等待）。首个候选目标为
两轮 P95 均 ≤ 2100.694 ms，比较快基线改善至少 20%。随后检查 app 1 MiB Source/Live
输入（约 207–213 ms）及批量插入（约 240–245 ms）的 UI 构建成本；CPU 归因后再冻结对应
目标。10 KiB Live 尾部、app 打开/保存作为后续调查和非目标观察项；不能从延迟直接断言根因。

验收：

- 编辑、保存、复制、撤销、中文/emoji/CRLF、跨块选择与 IME 仍保真；同时覆盖正常与降级状态。
- 在优化代码前写下目标场景与改善目标；首个热点目标已按上述基线冻结为至少改善 20%；其他目标在实现前依据归因明确，不是已有成绩或跨设备 SLA。
- 使用 R4-02 同配置做两轮完整候选；每轮核对源文/降级一致，非目标动作不得超出冻结的观察线。
- 结果达不到目标或布局方案需要架构重做时，保留数据、记录下一批边界，任务保持进行中或明确延期，不能仅凭“代码重构完成”关闭。
- 两个 Release main 验证编辑和文件闭环；不重做不相关平台矩阵。

建议提交：归因/方案 → 单路径实现与回归 → 配对结果、迁移说明（如有）与实际入口复验。

2026-10-14 上一批结果（PR #25）：四项 app 1 MiB 输入两轮均达到预先冻结的至少 20% 改善，
实际改善约 25%–31%；example Read→Live 仍为 2655.539 / 2657.556 ms，未达到
2100.694 ms。两种语义包装实验均撤回。55 项非目标中 53 项通过；app 10 KiB Live
输入/粘贴仍超原观察线，同环境旧实现完整控制轮也复现，不能据此放宽原线。
R4-03 保持进行中。原始数据、全量回归、Release 文件闭环及下一批原生生命周期
对照顺序见 [R4-03 报告](../benchmark/LARGE-DOCUMENT-COSTS-2026-10-14.md)。

2026-10-14 原生生命周期续批（PR #26）：保留未变化 Live 块身份，受限 TextKit 1
将 example 1 MiB Read→Live 两轮 P95 降至 1247.639 / 1352.428 ms，app 四项大文档
目标仍通过。本轮人工 IME、⌘S 续输和有限 VoiceOver 正常；两入口各两轮有效，另一次
窗口遮挡中断整轮排除。60 项中 56 项通过，原阈值与 `passed=false` 保留。

## R4-04 源码范围定位与视口保持

**使用场景：** 在长文中切 Source/Live/Read，打开另一文档后回来；定位到一个非标题的源码范围。

交付：在已有 `revealHeading` 上保留兼容，定义通用 UTF-16 范围显露和聚焦语义。视口状态与
Markdown/dirty/history 分离，由宿主持有文档身份；先支持同进程两个文档的模式/视口保持。
不承诺不同排版模式具有相同滚动像素，也不在这一步持久化整个编辑 State 或撤销栈。

验收：

- 定位普通段落、折叠标题内、表格单元格、隐藏语法附近与文档末尾，目标范围可见且不改原文。
- Read 超出预算前缀的目标返回明确结果/引导回 Source，不伪造“已显露”。
- 切模式保留阅读/编辑锚点；切文档不会串选区、焦点或滚动；文本缩短后范围安全收敛。
- 最新定位请求覆盖旧的异步滚动；替换 controller/卸载后不触发旧文档动作；外部输入有焦点时不擅自抢焦点。
- example 主入口通过两个内存文档演示，app 通过两个临时文件验证；不新增独立 demo 入口。
- 默认 View 数据更新回顶的现有契约不能静默更改；保持兼容默认或提供显式策略，并更新 API 基线与迁移。

建议提交：范围/锚点契约 → 组件实现 → 两入口接线及模式/文档切换回归。

## R4-05 当前文档查找与替换

**使用场景：** Cmd+F 查当前 Markdown，跳到下一处/上一处，在 Source/Live 替换并保存。

交付：核心提供可复用的匹配结果/范围与编辑操作，宿主决定搜索条布局和键位。首批只支持
字面文本、大小写选项、当前结果与下一处/上一处；然后增加单次/全部替换、明确的一次撤销语义。
搜索以完整原始 Markdown 为准，Read 的渲染文本不假装与源码一一对应；Read 允许查找，不直接替换。
正则、全工作区索引、模糊搜索和多文件替换不在本项。

验收：

- 两个 main 都能查找、导航、关闭搜索并回到编辑位置；app 原有 Search Files 不被覆盖。
- 中文、emoji、CRLF、反向查找、空查询、无匹配、重叠规则及超预算源文均有明确结果。
- 编辑后旧结果失效；异步搜索必须绑定文档身份/版本；结果范围始终指向当前源文。
- 单次/全部替换不误改未选范围，撤销/重做及 dirty 正确，保存重开字节一致；composing 时遵守 R4-01 策略。
- 1 MiB 查找有取消/结果数量与时间观测；显示结果可限制数量，但不能漏算或静默只替换前缀。

建议提交：查找与范围导航 → 两入口搜索条 → 替换/历史及大文档回归。

## R4-06 长会话资源与历史压力

**使用场景：** 用户持续编辑、切换/关闭多个文档，图表/资源晚到，随后继续在另一个文档输入。

交付：复用现有历史/流式/资源保护，在两个主入口增加固定的会话重放工作负载。example
用内存文档和可控异步 builder；app 用临时文件及实际 Mermaid。仅修复能证明归属的保留对象、
监听器、计时器和过期结果，不将核心包变成全局内存管理器。

验收：

- 每入口至少两次独立 30 分钟会话，固定 20 个文档、100 次打开/切换/关闭循环及输入/撤销动作；写明输入大小和并发资源数。
- 关闭后旧回调不能修改新文档；dispose 后无未处理异常，输入/历史不会串文档。
- 分别记录历史计账、活动 controller/订阅/请求数和进程 RSS；在同样检查点比较释放/平台缓存，不将 RSS 不立即下降直接判成泄漏。
- 如持续增长，必须以对象保留/订阅或缓存归因再修复；没有泄漏时交付有效证据和已知缓存上限即可，不能制造无依据的优化。
- 新的历史/缓存策略保持源码与保存基线；聚合文档数量/总内存策略属于宿主，核心只提供必要观测与释放契约。

建议提交：固定工作负载与计数 → 已复现问题修复（如有） → 两轮证据与宿主建议。

## R4-07 键盘与 VoiceOver 使用闭环

**使用场景：** 通过键盘及 macOS VoiceOver 识别模式、进入正文/表格、读取降级提示、操作搜索并返回编辑；属性操作只在已显示属性卡的 example 验证。

交付：先检查已有语义树、焦点顺序与动作标签，修复可复现缺口；随后在两个 Release main 中
执行实际 VoiceOver 任务。范围只覆盖本机明确记录的系统/SDK，保留局部可用与未覆盖的区别。

验收：

- 不使用鼠标完成模式切换、表格进出、搜索/关闭、文档切换；焦点可见且没有无法退出的循环。
- VoiceOver 能区分标题/正文/表格及当前模式，按钮有名称和可用状态；降级提示不重复混入正文选择或复制。
- 保留已有语义回归，再补真实任务脚本、系统版本、操作结果与发现问题；语义节点存在不能替代读屏实测。
- 需要人工操作时一次提供短脚本，沿用用户报告与工具观察分开的记录方式；未执行的读屏项保持待办，不能用 L08 中文输入结果代替。

建议提交：语义/键盘回归 → 修复 → 两入口实际任务记录。

## 暂不计入 R4 的候选

| 候选 | 暂缓原因 | 重新进入计划的触发条件 |
| --- | --- | --- |
| standard GFM 全流程编辑 | 正文/View 已支持；Live 的标准编辑会同时影响块模型、投影和输入映射，见 [现有决策](API_CONTRACTS.md#语法预设的范围r1-02) | example/app 明确需要编辑非 Obsidian 文档；先做语料与行为差异设计，再单独立项，不只向 Read 传 preset |
| 流式文档与异步资源的新 API | R2-03 已交付追加及旧结果隔离，不能重复造 document ID/cache 系统 | 两个 main 出现现有契约无法表达的实际需求，先用 host-owned 身份/版本复现 |
| 重启后恢复光标/滚动/撤销栈 | R3 已保证正文/dirty/模式恢复；持久化源码锚点需要版本迁移及外部文件变更策略 | R4-04 同进程契约稳定后，确有继续阅读位置的需求；撤销栈不默认持久化 |
| iOS/Web/Windows、SDK 升级和独立 AOT 复验 | 当前主线是两个本地应用；未完成的平台能力仍保留原记录 | 用户提出目标平台或分发需求后另开阶段；不等待上游才推进 R4 |
| 1.0 冻结、pub.dev 发布、真实外部产品 | 合入与本机验证不等于发布准备完成 | 用户恢复分发目标时，最后再提醒确定外部产品与平台矩阵 |
| 文件树/iCloud/Quick Look/应用外观 | 属于宿主产品，不能以数量稀释组件库主线 | 真正阻断上述组件任务时做最小宿主改动，其余单列 app backlog |

## 执行与交付约定

1. 从当前 main 建小分支；在 ROADMAP 领取一个任务。先记录触发条件和预期，不先假定需要重构。
2. 核心行为改变先加有区分力的回归；保留源码、选择、composing、历史和保存快照的边界。
3. 两入口测试固定使用实际 main/应用 Widget，GUI 固定实际构建路径和临时文件。
4. 实现批次执行适用的核心/宿主回归与 `make check-local build-local-release`；影响发布内容或公共 API 时执行 `make check-package`。公共变化同步契约、基线、迁移和入口说明。
5. 只改计划文档的批次检查引用、编号、数量、差异和发布清单；不为文案变化重复 GUI/全量原生构建。远端仍遵守已有 Core required 和被触发的 CI。
6. 每批按“实现/回归 → 文档/证据”提交推送；检查最终 PR 头，不能用前一个头的成功代替。
7. 记录通过、失败、未执行和兼容性成本；未达退出条件保持任务未完成。R0–R3 历史结论不随新增 R4 任务回退。

当前 R4-03 已完成续批全量回归、两个 main 各两轮配对、Release 操作和本轮人工复核；
五个预定优化目标通过，但四个小文档非目标场景仍超原观察线，任务保持进行中。
先按 R4-03 中的步骤区分帧构建、保存回调与输入法激活成本，再处理实现；不更改历史线，
不将有限 VoiceOver 复核扩展为 R4-07 全部通过，外部宿主仍留最终分发阶段。
